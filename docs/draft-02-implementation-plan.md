## Owner decisions D1–D5 (approved 2026-07-22, amended by owner review — record verbatim qualifications in decision records)

**D1 (B-02/A-15 + M-31 + A-05 structural core) — Global reject, no silent clamp; **typed calendar durations end-to-end** (no `_days` fields anywhere in v2).**
- **Wire model (mandatory — durations, not day-counts):** declarations, catalog minimums, audit records and error details all use ISO 8601 durations (delimited subset). No `declared_retention_days`/`minimum_retention_days` fields — `P6M` has no fixed day count, and day-typed fields would recreate the approximation M-31 eliminates. (What happens to the Draft-01 `retention_days` envelope field — replaced by `retention: "P180D"` — is settled in the D1 decision record as part of the v2 wire break.)
- **Normative comparison** (single rule): `declared_until = retention_anchor + declared_retention`; `minimum_until = retention_anchor + profile.retention_minimum`; `if declared_until < minimum_until → reject invalid_request`. If retention is **absent** → apply the profile minimum/default. ≥ minimum accepted (with data-minimization/storage-limitation language). No silent clamp, ever.
- **Error details:** `{profile, declared_retention, minimum_retention, retention_anchor, declared_retained_until, minimum_retained_until, resolution_source}`.
- **Single anchor rule (no `created_at`/`ts` alternatives):** the anchor is the instant the retention-bearing object was created/registered by the responsible party — audit records: the record's own `processed_at`/`created_at`; State entries: the entry's `created_at`; a message `ts` never starts retention of a record only received later. One anchor definition per object type, stated normatively.
- **Calendar arithmetic defined**, including end-of-month rule: `2026-08-31 + P6M = 2027-02-28`; `2028-08-31 + P6M = 2029-02-28` (clamp to last day of target month) — without this, implementations diverge.
- Catalog minimums: EU-AI-ACT-HIGH `"P6M"` (calendar), MIFID-II `"P1827D"`, DORA `"P1827D"`, PAC `"P1096D"`, DSA-VLOP `"P730D"` (pending M-02 730-vs-731), AI-ACT-LIMITED `"P90D"`, GDPR none.
- Floors are NOT automatically "legal minimums": per profile, `retention_basis: regulatory | profile_floor | technical_default | conservative_policy`, `retention_reference` (e.g. `EU-AI-ACT:26(6)`), `retention_interpretation: calendar-duration | day-count`.
- **A-05 structural core lands with D1 (one schema migration):** audit record gains `declared_retention`, `effective_retention`, `retention_anchor`, `retained_until`, `retention_source`, and declared-vs-resolved compliance-profile fields. Broader A-05 review (full resolved-value set, profile-absent case) completes in Phase 2 without further schema breaks.

**D2 (B-05) — Dual authorization + relay attestation, cryptographically bound.** Name: "end-to-end sender authorization + independently authenticated relay" (two authorities, not two interchangeable bearer tokens).
- Capabilities: `arsiaprotocol.broker.use` (delegable, "may request transport via broker") vs `arsiaprotocol.broker.relay` (registered Compliance Brokers only).
- Sender→broker: token sub=sender, aud=broker, scope ⊇ broker.use. End-to-end token: sub=from, aud=to, scopes = message capabilities, short TTL, preferably DPoP sender-constrained (jti, short acceptance window, nonce where needed — RFC 9449 scope limits acknowledged). Broker forwards the **byte-identical** envelope; Core §6.4 unchanged (direct and brokered indistinguishable at token validation).
- **Mandatory cryptographic binding between envelope, token, proof, and attestation** (no mix-and-match): the signed envelope carries an `authorization` reference (`{token_hash: "sha-256:…", proof_type}`), and/or the sender's proof binds `{message_id, envelope_hash}`. Net effect: sender signature binds envelope+token_hash; sender proof binds token+envelope_hash; relay attestation binds broker+envelope_hash+token_hash+policy. Exact placement decided in the B-05 decision record; binding is non-negotiable.
- **Hash definitions (mandatory, unambiguous):** `envelope_hash = SHA-256(JCS(complete signed envelope))` — **including** `security.sig`; the relay computes it over the envelope actually received/forwarded, binding the attestation to the transported message. This is distinct from `signing_input = JCS(envelope without security.sig)`; the two MUST NOT share one ambiguous definition.
- **Attestation format (complete, versioned):** `{v, attestation_id, broker_id, message_id, envelope_hash, authorization_token_hash, sender, recipient, residency_zone, received_at, forwarded_at, policy_ref (version/digest), issued_at, valid_until, security{alg, kid, sig}}` — canonical signing procedure (JCS, same signing profile), replay handling (attestation_id + acceptance window). `valid_until` bounds **acceptance during relay only** — it is not the end of the evidence's verifiability, and retention of the attestation is governed by profile/audit policy. Historical verification needs: broker key history + key status at signing date, policy digest, rotation/revocation chain (ties into A-18). Spec calls it **"relay evidence"** — attests the broker's claim, not physical residency proof (feeds A-14 honesty).
- **Normative transport mapping (mandatory, not "alongside"):** define exactly where each artifact travels, e.g. `Authorization: DPoP <sender-e2e-token>` + `DPoP: <sender-proof>` + `ARSIA-Relay-Authorization: <broker-token-or-proof>` + `ARSIA-Relay-Attestation: <encoded-attestation>`; alternative (transport container) compared in the decision record; one is chosen normatively, including the direct (non-brokered) case and WebSocket binding.
- Recipient verifies: message signature; e2e token (sub==from, aud==to); operation capabilities; broker identity/authorization; attestation (incl. hashes match); zone vs data_residency; envelope unaltered.
- RFC 8693 token exchange = **optional normative profile** (requires issuer trust/A-17 + PoP + audience policy), not the base flow, not discarded.
- **Order dependency (mandatory):** a minimal foundation slice of **A-17 (issuer trust)** and **A-01 (identity resolution)** MUST land before B-05 (see execution order).

**D3 (A-16) — Sign everything except `security.sig`; staged verification order.**
- Signing input = JCS(envelope with `security` present, **only the `sig` property removed** — not `sig: null`, not `sig: ""`, not a partially rebuilt `security` object; everything else byte-semantically present before JCS). Covers `alg`, `kid`, `encrypted`/enc metadata, and D2's `authorization.token_hash`.
- **Verification pipeline (normative order, mandatory):** (1) size limits → (2) JSON parse → (3) I-JSON conformance → (4) duplicate-key rejection → (5) minimal presence/shape of security fields → (6) version/signing-profile selection → (7) signing-input reconstruction → (8) key resolution (`kid` MUST identify a key of `message.from`) → (9) algorithm coherence: `security.alg` MUST be compatible with the resolved key AND the protocol allowlist; never selected from untrusted input alone; unknown/disallowed → reject → (10) signature verification → **only then** (11) full schema + semantic validation → (12) token/capabilities/compliance → (13) processing. Pre-signature validation is limited to what a safe verification needs — full schema/authorization/compliance run only after signature success (bounds unsigned-attacker work, avoids leaking semantic errors pre-auth, avoids premature forward-compat rejection, avoids profile resolution over unauthenticated input).
- Breaking crypto change ⇒ wire-version bump (D5), full re-sign of affected vectors, migration guide, no silent downgrade, unambiguous signing-profile identification.

**D4 (B-08 + A-20) — JSON value semantics + decimal-string amounts (corrected grammar).**
- State preserves JSON **value** and type, not lexical form (`1.0` ≡ `1`; returned values MAY use JCS canonical representation) — rewrite State §2.1.2; no literal round-trip requirement.
- Exact-precision values (Assets `amount` in request/receipt/reversal/escrow/MiFID record) = **decimal strings** with corrected canonical grammar:
  `amount = integer [fraction]` · `integer = "0" / non-zero-digit *DIGIT` · `fraction = "." 1*DIGIT` · `non-zero-digit = %x31-39` (the previous `"0" / positive-integer [fraction]` wrongly rejected `"0.01"`).
- Additional rules: no fraction when applicable scale is 0; for currency the fraction MUST have **exactly** the ISO 4217 minor-unit digits (fixed scale: EUR "1500.00", JPY "1500", KWD "1500.000") — **canonical equality made explicit in vectors**: for EUR, `"1500"`, `"1500.0"`, `"1500.000"` are all invalid, only `"1500.00"` valid; protocol limits on total digits, integer digits, max token scale, max string length; no exponent, no `+`, no whitespace/thousands separators/decimal comma, no leading zeros (except "0"), no NaN/Infinity; **no negative amounts in transfers/reversals — reversal is expressed by operation type with positive amount**; per-operation zero-allowed rule.
- **ISO 4217 entries without a numeric minor-unit exponent:** currency amounts MUST be rejected unless a profile or asset descriptor defines an explicit scale. Record the catalog edition/date used, its update procedure, behavior when sender and receiver use different editions, and expose the catalog version/digest via discovery or profile. Token/entitlement/service_unit precision per type or per descriptor. Never float internally (arbitrary decimal or integer minor units).
- Old numeric `amount` fails loudly (schema type error). **A-20 is thereby partially executed in Phase 1** — mark it so; Phase 3 only adds remaining language/tests, no second amount migration.

**D5 — Wire version `2.0`; explicit v1 policy (no-fallback, not blanket-reject).**
- Draft-02 defines **only v2 behavior** normatively. The essential security rule: **a message declared 2.0 is never reinterpreted/re-verified under 1.0 rules after failure** — `v==2.0` verification failure → reject, never "try v1".
- Legacy v1 support MAY exist as an explicitly configured **compatibility profile** with isolated verifiers (`v==1.0` → legacy verifier; `v==2.0` → v2 verifier), no implicit negotiation or fallback; implementations MUST NOT claim v2 security properties for v1 messages; regulated deployments can disable v1 entirely; discovery announces the versions actually accepted. Whether this repo's conformance targets v2-only is recorded as a deliberate operational decision, not a cryptographic necessity.
- **Conformance claims are isolated:** an implementation accepting both declares separately "ARSIA v2 conformant" and "ARSIA v1 compatibility enabled" — never a single ambiguous "ARSIA compliant" claim.
- Propagation: Core §4.1.1 + version prose, media type `v` param, discovery `protocol_version`/accepted versions, schemas pinning the major, examples, affected vectors, VERSIONING.md, FAQ. Supersedes the "one version, wire 1.0" project rule — Draft-02/v2 is the one version going forward (still: never defer fixes to hypothetical future versions).
- **Selective vector update (mandatory — not "all 613 to v2"):** all message-only and applicable hybrid vectors move to v2 envelopes; schema-ref vectors are updated **only when their target schema changed**. The regeneration script computes the affected set and logs it.

## Predetermined directions (clear in the audit — no further human input needed)

- **B-01 (+ mandatory root identifier):** `correlation_id` = id of the **immediately previous message** (immediate causal parent; align Core §2.2 to §4.2.1/Actions §3.3). In addition, a uniform **root identifier** (`root_request_id`, or `original_request_id` if the existing name is kept — but then promoted to a uniform envelope/cross-cutting contract, not a per-payload field) is **REQUIRED in every message of a multi-step interaction**: for the initiating request it is absent or equals `id`; for `pending_approval`, `approval_decision`, final response, timeout, receipts and errors it MUST equal the initiating request's id. Rationale: with correlation-to-previous only, the original requester may never have seen the intermediate message (A→B request R; B→C pending P; C→B decision D; B→A response S with `correlation_id = D.id` is unmatchable by A). Enables causal walk, requester matching, audit query per interaction, multi-party approval, second receipt (A-11), timeout — without private knowledge. This lands **in B-01**, not deferred to H3. Specify unknown/duplicate/late correlation handling.
- **B-03:** standardize **1827** (FAQ rationale) in Assets §6.1.2/§3.1.2/§3.2.2/§3.3.3, Actions §2.1/§7.2, Identity §9.3, ASSETS-07; anti-regression vector + constant-consistency check.
- **B-04:** Actions §1.4 becomes the single normative registry of reserved capabilities, adding `echo`, `health`, `onboarding.evaluate`, `broker.use` (D2), with an explicit rule for example/policy capabilities (`code.review`, `code.refactor`, `test.unit` — register or move off the reserved prefix) and an extension rule for the `arsiaprotocol.` namespace.
- **B-06:** canonical `pending_approval` = Actions §3.2/Core §4.4.7/schema (`payload.args`; enums `approved|denied` / `denied|expired`); rewrite Assets §5.2, ASSETS-06, `human_oversight_status`; cover approval/denial/timeout/invalid decision.
- **B-07:** one capability-matching algorithm defined once (Core §6.4 or Actions §1.2), referenced from the other: exact match after explicit wildcard-expansion rules (wildcard only final segment; no mid-name; no bare `*`; non-delegable never wildcard-matched); the mission's 11 positive/negative cases as vectors.
- **M-25 → reclassify HIGH:** signed envelope `idempotency` prevails over unsigned `Idempotency-Key` header (header must match or be ignored/rejected); anti-replay note in §13.2.2. **M-27:** fix `dora_incident` name + premature trigger (Assets §6.2.4 disclaimer already exists). **M-28** anchor = Actions §5.2; **M-29** = Actions §4.4.
- **A-19/A-21:** conditional language / "technical contribution, subject to legal review" — no definitive legal claims. **A-22:** state exactly which tamper classes are detected (modification, removal, truncation, full rewrite, fork) and which are not.
